# 上次决赛代码对 2026 决赛的兼容性分析

## 结论

上次决赛的避障思路和控制器状态机可以作为候选基线，但不能把 `APF.mo` 或 `for_code.mo` 整体直接烧录到本届车辆。正确做法是：保留本届官方 `for_code_ZXDJ520.mo` / `for_code_JGB520.mo` 的传感器采集、舵机、电机驱动和代码生成配置，只移植并重新标定上届控制算法。

## 可复用部分

- `Controller/APF.mo` 和 `Controller/ObsAvoidController_Sysblock7g.mo` 中的前、斜前、左右测距避障逻辑。
- 前进、后退、脱困和转向状态机的总体结构。
- 20 ms 控制周期、超声测距预处理和舵机命令的基本思路。
- 上届阈值可作为首次台架试验的起点，但不能直接当本届最终参数。

## 不能直接复用部分

1. **电机接口已经改变。**上届 `vehicle_speed(speed, gap)` 在 C 层把速度和差速混成左右轮；本届官方模型分别输出 `left_speed`、`right_speed`，并按 ZXDJ520/JGB520 提供不同驱动源文件。
2. **传感器语义存在冲突。**硬件注释写的是 1=正前、2=前方舵机、3=右、4=左、5=后；本届 ZXDJ520 内部状态机端口却按 `df/db/dr/dl/dfu` 接入 1–5。必须用手挡传感器逐个核对实际通道后再接算法，不能只信变量名。
3. **控制器已经不是同一版本。**例如上届 `ObsAvoidController_Sysblock7g.mo` 约 36 KB，本届版本约 81 KB；状态和参数已明显改动，不能假定行为相同。
4. **本届有双车和坡道场景。**上届逻辑主要针对静态边界/障碍，没有可靠的对手车判别，也没有按坡道区域降速、禁止激烈反转和出坡恢复的专门状态。
5. **整车封装和生成配置过时。**上届包装模型仍调用旧的 `vehicle_speed(double,double)`，而本届官方外部接口调用 `vehicle_speed(int,double)` 分别驱动左右电机。整体替换会绕开本届电机型号适配和安全停机配置。

## 推荐迁移顺序

1. 先选定实车电机型号，只以对应的本届官方 `for_code_*.mo` 为硬件壳。
2. 做五路传感器遮挡测试，形成“物理方向—dis 编号—控制器端口”唯一映射。
3. 把上届 APF/7g 作为纯控制子模块接入，输出转换为左右轮速度和转向，不拷贝旧 C 驱动。
4. 在 `FinalRace2026.Track1` 上比较碰撞量、脱轨量、60 s 前进距离和是否卡死。
5. 加入坡道模式：入口降速、限制转角/差速、禁止长时间倒车，离开坡道后用滞回恢复正常速度。
6. 最后进行双车测试；动态目标连续逼近时优先减速/停车，不把另一辆车当作必须绕过的固定障碍。

## 当前基准结果

`FinalRace2026.Track1` 已通过 Sysplorer 模型检查和 0–60 s 仿真。60 s 时车辆约位于 `(-7.80, 47.68)` m，说明初赛控制器能驱动车辆进入赛道主要弯道，但碰撞累计量较高，当前只适合作为“可运行基线”，不适合直接参赛。
